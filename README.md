# O2Ban Validation Workspace — v0.4 Automotive Pilot — Reference Data & UX Hardening

نسخه ارتقایافته پایلوت مستقل O2Ban برای آزمون چهار نقش بازرگانی در صنعت خودرو؛ با رابط فارسی و راست‌چین و واکنش‌گرا (موبایل، تبلت و دسکتاپ)، ASP.NET Core 10، EF Core 9 و MariaDB 11.4 LTS. برنامه و دیتابیس در Docker Compose اجرا می‌شوند.

> این نسخه یک پایلوت عملیاتی برای آزمون گردش‌کار است، نه نسخه نهایی معماری سازمانی O2Ban. داده‌ها ساختگی‌اند و هیچ ادعای اعتبارسنجی مستقل درباره شرکت‌های نمونه ندارند.

## تغییرات نسخه ۰.۴

- جدول مرجع `LookupOptions` در MariaDB برای گروه کالایی، واحد اندازه‌گیری، اولویت، وضعیت شواهد، بخش تأمین‌کننده و وضعیت درخواست.
- ایجاد/تکمیل جدول مرجع به‌صورت افزایشی و تکرارپذیر؛ مناسب دیتابیس‌های موجود v0.2/v0.3 و بدون حذف داده‌های قبلی.
- انتقال مقادیر متنی قدیمی گروه، واحد، اولویت و وضعیت شواهد به فهرست‌های مرجع برای حفظ سازگاری.
- کمبوباکس گروه کالا، واحد، اولویت و وضعیت شواهد از API متصل به MariaDB تغذیه می‌شود؛ اعتبارسنجی سمت سرور نیز همین مقادیر را کنترل می‌کند.
- فونت Vazirmatn با fallback محلی و بهبود نمایش فرم‌ها و کنترل‌ها در موبایل.
- Health readiness تعداد گزینه‌های مرجع فعال را کنترل می‌کند و در صورت ناقص بودن اطلاعات پایه پاسخ آماده نمی‌دهد.

- نمایش واکنش‌گرا: در نمایشگرهای کوچک جدول‌ها به کارت‌های خوانا تبدیل می‌شوند و منوی کناری به منوی موبایل تبدیل می‌شود.
- موتور تطبیق اولیه با تفکیک امتیاز عوامل، هشدارهای شواهد و پرچم عدم صلاحیت اولیه؛ امتیاز ابزار غربالگری است و تأیید نهایی نیست.
- واژگان یکسان وضعیت شواهد در فرم و داده‌های پایه: اعلام‌شده، دارای مدرک، تأییدشده توسط شرکت، نیازمند به‌روزرسانی، دارای تناقض، مشکوک و ردشده.

- ورود چهار کارشناس آزمایشی و یک مدیر آزمایشی
- داشبورد، شرکت‌های هدف، تأمین‌کنندگان، کاتالوگ کالا
- درخواست خرید و کشف اولیه تأمین‌کننده
- استعلام RFQ و ثبت پیشنهادها
- ثبت ادعا/شواهد و بازخورد کاربران
- گزارش پایه
- ثبت تأمین‌کننده با نام شرکت، شناسه ملی اختیاری، شهر، نام رابط، توانمندی‌ها، شرایط پرداخت، زمان تحویل و وضعیت شواهد
- اعتبارسنجی سمت سرور برای فیلدهای ضروری تأمین‌کننده و شناسه ملی؛ شناسه ملی خالی مجاز است و در صورت ورود باید ۱۱ رقم باشد
- جلوگیری از شناسه ملی تکراری در صورت ثبت مقدار
- Health endpoint برای بررسی زنده‌بودن برنامه و اتصال دیتابیس

## راه‌اندازی روی سرور Linux

1. فایل ZIP را روی سرور استخراج کنید.
2. فایل متغیرهای محیطی را بسازید و رمزهای قوی قرار دهید:

```bash
cp .env.example .env
nano .env
chmod 600 .env
```

3. سرویس‌ها را بسازید و اجرا کنید:

```bash
docker compose up -d --build
```

4. وضعیت سرویس‌ها را بررسی کنید:

```bash
docker compose ps
docker compose logs -f app
curl http://127.0.0.1:5080/health/ready
```

5. پورت برنامه فقط روی `127.0.0.1` میزبان منتشر می‌شود؛ دسترسی کاربران را از طریق دامنه HTTPS و Reverse Proxy برقرار کنید.

**امنیت استقرار:** TLS/HTTPS باید در Reverse Proxy فعال باشد؛ در محیط Production کوکی ورود Secure است. پورت MariaDB عمداً به میزبان منتشر نشده است. رمزهای `.env` را در Git یا فایل ZIP عملیاتی قرار ندهید. نمونه مقصد Reverse Proxy برابر `http://127.0.0.1:5080` است.

راهنمای کامل کارشناس‌ها و الگوی ثبت بازخورد در فایل `PILOT-USER-GUIDE.md` قرار دارد.

## داده‌های اولیه

در اولین راه‌اندازی، Seeder اطلاعات پایه آزمایشی را در MariaDB درج می‌کند. داده‌های پایه فعلی شامل ۵ حساب (۴ کارشناس و ۱ مدیر)، ۱۲ شرکت هدف، ۱۳ تأمین‌کننده، ۱۸ قلم کاتالوگ، ۸ درخواست خرید (حداقل ۲ سناریو برای هر نقش)، ۸ RFQ، ۹ پیشنهاد و ۱۸ رکورد شواهد است. سناریوها در چهار مسیر زیر طراحی شده‌اند:

| حساب | حوزه آزمون | سناریوهای آماده |
|---|---|---|
| expert1 | بازرگانی داخلی، قطعات تولیدی | براکت نگهدارنده موتور، بوش لاستیکی طبق |
| expert2 | بازرگانی داخلی، اقلام غیرتولیدی | فیلتر روغن خط تولید، کارتن بسته‌بندی قطعات |
| expert3 | بازرگانی خارجی، قطعات تولیدی | سنسور فشار روغن، بلبرینگ چرخ |
| expert4 | بازرگانی خارجی، اقلام غیرتولیدی | کولیس دیجیتال، ابزار گشتاور |

همه نام شرکت‌ها، اشخاص، قیمت‌ها، پیشنهادها، شرایط تجاری و وضعیت‌های نمونه ساختگی‌اند. اطلاعات گواهی یا سند به معنی وجود فایل واقعی نیست؛ مواردی که یادداشت آن‌ها صریحاً می‌گوید فایل ضمیمه نشده، فقط برای آزمون گردش‌کار هستند. Seeder اجرای مجدد را بدون تکثیر رکوردهای نمونه انجام می‌دهد و وضعیت قدیمی «دارای مستندات» را برای رکوردهای نمونه به وضعیت واحد «دارای مدرک» تبدیل می‌کند. در پایان، تعداد حداقلی داده‌ها و وجود سناریوی هر چهار نقش کنترل می‌شود؛ اگر داده‌ها ناقص باشند، راه‌اندازی با خطای روشن متوقف می‌شود.

## آزمون خودکار پس از استقرار

پس از بالا آمدن برنامه و فعال‌شدن Reverse Proxy/HTTPS، از پوشه پروژه اجرا کنید:

```bash
python3 tests/smoke_test.py https://your-o2ban-domain.example
```

این آزمون ورود، وضعیت سلامت، همه مسیرهای GET، وجود داده اولیه، درج شرکت، اعتبارسنجی نامعتبر تأمین‌کننده، درج صحیح تأمین‌کننده، کالا، درخواست خرید، تطبیق، RFQ، پیشنهاد، شواهد و بازخورد و خواندن مجدد داده‌ها را بررسی می‌کند. این اسکریپت چند رکورد با پیشوند TEST در دیتابیس ایجاد می‌کند؛ پس از آزمون آن‌ها را بازبینی و پاک کنید.

همچنین بررسی نحوی JavaScript:

```bash
node --check wwwroot/app.js
```

## نگهداری و پشتیبان‌گیری

```bash
# backup
docker exec o2ban-mariadb sh -c 'mariadb-dump -u root -p"$MARIADB_ROOT_PASSWORD" o2ban' > o2ban-backup.sql

# restore (روی دیتابیس مقصد خالی/مناسب)
docker exec -i o2ban-mariadb sh -c 'mariadb -u root -p"$MARIADB_ROOT_PASSWORD" o2ban' < o2ban-backup.sql
```

برای محیط عملیاتی، خروجی Backup باید رمزگذاری و بازیابی آن به‌صورت دوره‌ای آزمایش شود.

## نکات فنی و محدودیت‌های فعلی

- راه‌اندازی اولیه Schema با `EnsureCreated` انجام می‌شود تا دیتابیس خالی MariaDB برای پایلوت آماده شود. این روش جایگزین EF Core Migrations برای چرخه انتشارهای بعدی نیست؛ قبل از تغییرات Schema در نسخه‌های بعدی باید Migration baseline و برنامه ارتقای دیتابیس تعریف شود.
- نسخه فعلی هنوز تمام معماری هدف Modular Monolith، Multi-Tenancy واقعی، روابط کامل با Foreign Key، تاریخچه تغییرات و RBAC تفصیلی سند معماری v1.0 را پیاده نکرده است. این موارد باید در فازهای بعدی اجرا شوند.
- موتور تطبیق، قاعده‌محور و ابتدایی است؛ امتیاز آن بر اساس هم‌پوشانی متنی، زمان تحویل، وضعیت شواهد، ثبت شرایط پرداخت و تناسب دامنه داخلی/خارجی محاسبه می‌شود. این الگوریتم هنوز مدل یادگیری ماشین یا تطبیق مهندسی قطعه نیست؛ تصمیم خرید باید انسانی باشد.
- RFQ در این نسخه داخل سامانه ثبت می‌شود؛ ارسال ایمیل/SMS یا ارتباط خودکار با تأمین‌کننده انجام نمی‌شود.
- این محیط از SQLite و SQL Server استفاده نمی‌کند؛ Provider نسخه حاضر MariaDB است.
- نسخه فعلی برای پایلوت کنترل‌شده است، نه استقرار عمومی یا استفاده از داده واقعی حساس. پیش از استفاده عملیاتی باید Migrationهای EF Core، جداسازی سازمانی و مجوزهای ریزدانه، ثبت رویداد ممیزی، محدودسازی درخواست ورود، CSRF، مدیریت فایل مدارک، و آزمون بازیابی Backup تکمیل شوند.
- تست Build و تست یکپارچگی واقعی نیازمند اجرای Docker Build و Docker Compose در محیط دارای Docker و دسترسی به NuGet است.


## ارتقای v0.3 به v0.4

نسخه ۰.۴ به‌صورت additive طراحی شده است: روی دیتابیس موجود، جدول `LookupOptions` را در صورت نبودن ایجاد می‌کند و داده‌های مرجع را بدون حذف رکوردهای قبلی درج می‌کند. مقادیر قدیمی متنی موجود در کالاها، درخواست‌ها و وضعیت شواهد نیز به فهرست انتخابی وارد می‌شوند تا داده‌های قبلی قابل مشاهده و انتخاب باقی بمانند.

**پیش از استقرار روی دیتابیس اصلی، حتماً Backup بگیرید و ابتدا همین بسته را روی Restore آزمایشی اجرا کنید.** این نسخه هنوز از `EnsureCreated` برای ایجاد اولیه جداول اصلی استفاده می‌کند؛ جدول مرجع با دستور `CREATE TABLE IF NOT EXISTS` به شکل افزایشی اضافه شده است. این روش Migration کامل EF Core برای تغییرات پیچیده آینده نیست.

## کنترل سریع اطلاعات پایه

پس از ورود با یکی از کاربران آزمایشی، مسیر `/api/lookups` را باز کنید. پاسخ باید شامل گروه‌های `product-category`، `unit`، `priority` و `evidence-status` باشد. انتظار می‌رود حداقل ۱۲ گروه کالایی، ۱۷ واحد، ۳ اولویت و ۷ وضعیت شواهد وجود داشته باشد. آزمون خودکار این مقادیر در `tests/smoke_test.py` اضافه شده است.

## دامنه آزمون انجام‌شده در ساخت این بسته

- بررسی نحوی JavaScript با `node --check`.
- بررسی نحوی فایل آزمون Python با `py_compile`.
- بازبینی ایستای مسیر Seeder، API اطلاعات پایه، فرم‌ها و قواعد اعتبارسنجی.
- Build دات‌نت، اجرای Docker Compose و آزمون واقعی MariaDB در محیط ساخت انجام نشده است؛ چون Docker و .NET SDK در محیط ساخت در دسترس نبودند. برای تأیید اجرایی، پس از استقرار آزمایشی، فرمان‌های بخش «آزمون خودکار» را اجرا کنید.

## محدودیت‌های محصول که عمداً در این نسخه ادعای رفع آن‌ها نمی‌شود

این نسخه اصلاح داده‌های مرجع و تجربه کاربری است، نه تکمیل تمام معماری سازمانی. هنوز مواردی مانند روابط FK کامل بین کالا و تأمین‌کننده، پروفایل ساختاریافته ظرفیت تأمین‌کننده، مدیریت فایل واقعی شواهد، گردش‌کار مستقل ممیزی، چندسازمانی واقعی، RBAC ریزدانه، Audit Trail جامع و موتور تطبیق مهندسی قطعه در دامنه نسخه بعدی هستند. امتیاز تطبیق همچنان ابزار غربالگری قاعده‌محور است، نه تأیید صلاحیت یا توصیه خودکار خرید.
